# Правила, применение и цепочки

## Первый маршрут

1. Запустите узел и панель по инструкции для своей платформы. Убедитесь, что ядро работает.
2. В панели создайте нужный выход и правило, которое выбирает его для тестового домена.
   Начните с одного домена или клиента, чтобы результат было легко проверить.
3. Откройте раздел изменений и изучите черновик. Проверьте адрес выхода, DNS
   и доступ к панели после переключения.
4. Примените изменения временно. Проверьте DNS и запрос через выбранный маршрут,
   затем подтвердите применение в указанный панелью срок.
5. Если проверка не прошла, верните прежнюю конфигурацию. Без подтверждения
   временное применение откатится по истечении срока.

Набор разделов зависит от режима. Нативные Linux VPN-службы, AdGuard и прозрачный
LAN-вход недоступны локальному переносимому узлу. Системный шлюз macOS настраивается
отдельным административным CLI, по [своей инструкции](macos-gateway.md).

## Проверить локальный узел

Из каталога проекта:

```sh
.venv/bin/python tools/local_node.py status
curl --proxy socks5h://127.0.0.1:2081 https://example.com/
```

`socks5h` передаёт разрешение имени через прокси. Успешный запрос проверяет этот
путь, но не доказывает, что другие приложения или вся LAN используют его.
Для DNS можно выполнить `dig @127.0.0.1 -p 5301 example.com`, если установлен `dig`.
Выберите свои доступные тестовые адреса; их доступность зависит от вашей сети.

## Соединить узлы

Сначала проверьте каждый узел отдельно, затем настройте защищённый транспорт
между ними и выход первого узла через второй. Правила следующего узла
применяются к трафику, который он получает; исходный адрес устройства может
не сохраняться при передаче через прокси.

Пример подключения к loopback SOCKS-порту Linux-узла через SSH:

```sh
ssh -o StrictHostKeyChecking=yes -N \
  -L 127.0.0.1:12081:127.0.0.1:2081 user@linux-host
```

Предварительно проверьте ключ SSH-хоста доверенным способом. Пока команда
работает, `127.0.0.1:12081` на первой машине ведёт к прокси второй. Используйте
этот адрес для SOCKS-выхода или отдельной проверки:

```sh
curl --proxy socks5h://127.0.0.1:12081 https://example.com/
```

После настройки цепочки проверьте выбранный выход и поведение при разрыве
туннеля. Прямой запасной маршрут, если вы его задали, меняет поведение отказа.
Проверка одной цепочки не гарантирует отсутствие обхода в любой политике.

## Состояние и восстановление

Закрытие веб-панели не останавливает supervisor локального узла. На Mac его
автозапуск описан в [инструкции macOS](macos.md). После потери ответа на применение
сначала перечитайте статус и раздел изменений: действие могло уже выполниться.

Для Linux храните ключ восстановления отдельно от зашифрованного архива,
проверьте вход на `/recovery/login` и отработайте восстановление на отдельной
машине. Политика маршрутизации и полный системный архив решают разные задачи;
перед восстановлением прочитайте состав и область действия выбранного архива.
